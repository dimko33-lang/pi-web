# v0.14.0 — installing the reference application

**A clean installation on Ubuntu 24.04 has not yet been tested.** This is a fresh-host release, not an in-place upgrade from v0.13.0. Take a machine snapshot before installation. Keep any instance backup private. Do not try this installer on the reference host.

## One command

On a new Ubuntu Server 24.04 **x86-64** system, as root, with systemd, at least 2 vCPUs, 4 GiB RAM recommended, 18 GiB free and inbound TCP 80/443:

```sh
curl -fsSL https://dimko33-lang.github.io/pi-web/install.sh | bash
```

For a sudo login use `curl -fsSL https://dimko33-lang.github.io/pi-web/install.sh | sudo bash`. The card's `/install` URL redirects to this same bootstrap. It checks the release archive against a SHA-256 pinned in the launcher before extracting into a private temporary directory (not `/`). The new application does not require a GitHub account, Telegram account or model-provider login to install. Network access to Ubuntu, Node, npm, PyPI, Docker registries, Playwright and speech-model distribution sites is required. Allow time and disk space for Chromium, speech assets and the two project images.

The default base name is the public IPv4 with dashes under `sslip.io`; panel, editor, public project and reader get separate HTTPS hosts. No credentials are shared through DNS. If the server is behind NAT, set `PI_WEB_PUBLIC_IP` explicitly. Alternatively, set `PI_WEB_DOMAIN` to a domain **you control**; point its apex, `www`, `panel`, `pi`, `editor`, `www.editor` and `arri` records to this host (check IPv6 if present). For example, in a root shell: `export PI_WEB_DOMAIN=lab.example.org` **before** the curl command. Passing variables to `curl` instead of `bash` does not configure the installer. If using sudo pass the desired settings to `sudo env ... bash` on the right side of the pipe. Public ACME issuance depends on correct DNS, reachable port 80 and CA limits. For a deliberate private TLS test, `PI_WEB_TLS=self-signed` requests a new local 30-day certificate instead; clients will need to trust it explicitly. There is no silent downgrade to HTTP or anonymous access.

The installer verifies an empty destination, creates separate service principals and fresh passwords, mounts an ext4 CurveLab project image, stages the source, installs locked application dependencies, builds the science and project images, provisions TLS, then checks the protected routes. Before the app is ready only the ACME challenge is served. It never copies an existing Telegram session or sends a message. Installation stages checkpoint under root-only `/var/lib/pi-web-installer`. On failure, read the error, correct the cause and rerun the **same** command. A successful rerun does not reinstall or reset chats/profiles. This resume path has not been verified on a rebooted Linux machine.

On success the installer prints the private panel URL; root can recover it from `/var/lib/pi-web-installer/access.txt`. Treat the query key as a password. The editor has a **separate** login; its key is in `/etc/curvelab-editor.env`, not the panel cookie. Configure browser Pi with `sudo -u pi-browser -H /usr/local/bin/pi` from a directory accessible to that user. Select and authorize your own model there. Do not authorize Pi as root expecting the panel to inherit it. Root mode in the panel is initially **off**; the owner can explicitly enable host administration. Do not share the owner link with other users.

## Private inputs and Telegram (not part of installation)

Fresh group/DM settings are independent; slots are present without importing people, history, individual guest profiles or private prompts. By default the code is rendered with **unbound** identities. For a real Telegram instance, supply your **own** bindings before first installation: `PI_WEB_BINDINGS=/root/my-bindings.json`. This file is a root-only JSON object; see [binding schema](../deployment/bindings.json) and [source map](reference-install.md). Supply actual owner/account identities, relevant chat and channel IDs, handles and, if needed, your avatar; unspecified identities remain unbound. Never use the test fixture as a real config. Peer magnitudes are positive strings, not aliases. Private overrides are validated before rendering. Real bindings, entry keys and rendered files remain outside Git. Save `/var/lib/pi-web-installer/inputs.json` privately; changing it alone later does **not** rewrite the deployed code. To change bindings on an existing instance, stop affected units, use `tools/prepare.py` with the full new private binding map to render a separate staging tree, and review/apply just the changed paths and the profile catalog; never overwrite live data or rerun setup over another host.

Telegram remains **disabled**. The account service and the two collectors also have an enrollment condition. To enroll separately:

1. Confirm either a genuinely independent account or a fenced cutover with the previous client and collectors stopped. Use actual bindings, not the unbound defaults. Supply `/etc/pi-web-instance/telegram-client.json` with integer `api_id`, string `api_hash` and an optional Telethon proxy. Keep it root-owned, mode 0600, then grant only `pi-nikita` a read ACL. Configure the account's own prompts, Telegram-side Pi authorization and any individual DM catalog entries privately. Its Pi home is `/srv/pi-workspaces/nikita/rootfs/opt/projects/tg-agent/home`, not the browser home.
2. While services are stopped, create the **new** Telethon `account.session` interactively as `pi-nikita` in `/opt/tg-agent` using its installed venv, `config.API_ID`, `config.API_HASH` and `config.PROXY`. Verify `get_me().id` against the privately bound account ID and disconnect before starting any unit. Restrict the session to mode 0600. The reference `nikita-tg-login` helper is for replacing an **existing** session, not for first installation.
3. Only after verification, as root create `/etc/pi-web-instance/telegram-enrolled` (0600) and explicitly enable/start `tg-agent.service`. Inspect its status and delivered reply before optionally enabling `nikita-salon-history.timer` and `nikita-salon-piwep.timer`. No incoming chats are replayed by the installer. Removing the gate prevents future starts; to fence a running host stop the service, collectors and timers first.

Optional providers use the actual socket services and their `LoadCredential` paths. Gacrux uses `google-key` and the reference `enabled` marker; Anam uses `anam-key` and an enrolled avatar. HeyGen is opt-in and requires its own key, trusted portrait and explicit `circle-provider` selection. The instance directory is `/etc/pi-web-speech/` followed by the 12-character hash computed from the Telegram venv path. Keep keys and portraits root-only. Image authorization goes in the worker's own private state, not the project source. No provider calls or paid generations are part of acceptance. Missing credentials do not imply a different fallback implementation.

## Portability decisions and acceptance

- The actual nginx `Save` route invokes the private reference exporter. Its output can contain sessions, chats and credentials. **Never publish that archive.** This is not a new encrypted private-state recovery system.
- All reference vhosts share one newly issued multi-name certificate on this machine; cookie scopes, auth subrequests and actual handlers stay separate. Renewal uses the permanent webroot plus a checked nginx reload. In root-only diagnostics use `nginx -t`, not `nginx -T` in logs (the latter dumps private access maps).
- Reuse the checked panel's `models.json` and offline metadata reader in the separate Telegram panel path; no shared browser home or auth. Seed empty stores with their actual schemas. Preserve the shared profile ACLs. The nine fresh profile slots are seven group roles, owner DM and default guest DM; enrolled individual peers are private state, not shipped demo users.
- CurveLab workload UID 1000 is scoped beneath a root-only mounted volume. The editable worktree and release have their own locked npm installs. Use the actual loopback editor until a release is explicitly published. Science retains the same worker, image and isolation options; on installation the four-CPU ceiling and its two thread counts are capped by available Docker CPUs and affinity. No production unit is changed by this adaptation.
- Inspect `systemctl --failed`, the mounted project volume, actual browser/Telegram UID isolation, reader grants, authenticated Save, editor and panel writes. Verify reboot and rerun leave state intact. Test Telegram, science, PDF/media and provider behavior **after separate enrollment**. Local source/fixture/HTTP checks are not these Linux tests.

To roll a machine back, preserve new private data separately and revert the pre-install machine snapshot (or start on another clean host). Do not run the legacy uninstaller against this system deployment. Rolling the public card back is a separate Git operation: restore the old Pages launcher/card at the previous commit, leaving versioned releases intact.
